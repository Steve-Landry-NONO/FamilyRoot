# Runbook — Local Setup

Use this runbook to prepare a reproducible FamilyRoots development environment.

## 1. Prerequisites

Required locally:

- Git
- Node.js/npm compatible with the backend dependencies
- Flutter SDK compatible with Dart `^3.6.1`
- access to the intended Supabase development project
- a PostgreSQL/Supabase database connection usable by Prisma

Do not reuse production credentials for routine local development.

## 2. Clone and branch

```bash
git clone git@github.com:Steve-Landry-NONO/FamilyRoot.git
cd FamilyRoot
git checkout develop
git pull --ff-only
```

For work, create a dedicated branch from `develop`.

## 3. Environment configuration

Start from the repository template:

```bash
cp .env.template .env
```

Inspect `.env.template` and provide the values required by the target development environment.

Rules:

- `.env` must remain uncommitted;
- never paste real secrets into documentation or PR descriptions;
- if a required variable is missing from the template, update the template with a safe placeholder in the same PR.

The backend loads `.env` through NestJS `ConfigModule`.

## 4. Backend setup

```bash
cd src/backend
npm ci
```

If Prisma client generation is required:

```bash
npx prisma generate
```

Validate the schema against the configured database only when credentials are available:

```bash
npx prisma validate
```

Start development server:

```bash
npm run start:dev
```

The GraphQL schema is generated by NestJS into `src/backend/src/schema.gql`.

## 5. Mobile setup

From repository root:

```bash
cd src/mobile
flutter pub get
flutter analyze
```

Run the app on an available target, for example:

```bash
flutter run -d chrome
```

Use the environment/config mechanism already present in `lib/core/config/`; do not hard-code a local backend URL into feature code.

## 6. Basic smoke checks

Backend:

```bash
cd src/backend
npm run build
npm test -- --runInBand
```

Mobile:

```bash
cd src/mobile
flutter analyze
flutter test
```

If no Flutter tests are currently present, `flutter test` may report that fact; do not treat absence of tests as adequate coverage for new work.

## 7. Database changes

Before editing `schema.prisma`:

- read `AGENTS.md` and `RULES_ESCALATION.md`;
- determine whether the change requires human approval;
- never apply a destructive migration to a shared/production database during local setup.

For an approved development migration, use the project's Prisma workflow and include the migration files in the PR.

## 8. Troubleshooting checklist

If backend cannot start:

1. verify `.env` exists in the expected working directory;
2. verify DB/Supabase connectivity;
3. run `npx prisma validate`;
4. run `npm run build` for clearer TypeScript errors;
5. inspect the first root-cause error, not only downstream stack traces.

If Flutter cannot call GraphQL:

1. verify backend is actually reachable from the selected Flutter target;
2. verify GraphQL endpoint configuration;
3. verify Supabase session/JWT is present when the operation is protected;
4. inspect GraphQL `errors` as well as HTTP status;
5. verify schema/client query compatibility.

## 9. Ready-to-work criteria

Environment is ready when:

- dependencies install cleanly;
- backend builds and starts;
- Flutter analyzes and starts on a target;
- the intended development Supabase environment is reachable;
- no production secret is being used unnecessarily;
- the working branch is not `main` or `develop`.
